⚠️ Основное правило:
Перед тем как вносить изменения в любой файл, необходимо показать diff и дождаться подтверждения.

1. Общие правила

Не переписывать проект целиком и не менять архитектуру без прямой команды.

Любое крупное изменение — сначала обсудить и предложить варианты.

Не генерировать файлы, если не попросили.

Перед тем как что-то менять — добавить все связанные файлы в контекст.

2. Работа с базой данных (Supabase)

Не изменять существующие таблицы, колонки, типы данных или связи без явного разрешения.

Не менять RLS-политики, если не сказано в задаче.

Когда предлагаешь миграцию:

сначала описать логику изменения,

затем показать SQL,

затем дифф,

затем ждать подтверждения.

3. Работа с фронтендом (React + Vite + Tailwind)

Следовать текущему стилю кода проекта.

Не менять существующие компоненты, если задача не требует этого.

Новые компоненты — создавать рядом со связанными (внутри src/modules/...).

Не переименовывать файлы и директории.

Tailwind-классы использовать в текущей стилистике — не переделывать структуру.

4. Работа с API и запросами к Supabase

Перед изменением любого запроса нужно проверить схему таблиц.

Не добавлять новые поля в запросы, если их нет в таблицах.

Всегда уточнять, нужна ли модификация схемы.

5. Логика работы

Перед генерацией больших изменений (новых страниц, модулей, фичей) — писать краткий план и ждать подтверждения.

Любую сложную часть проекта анализировать перед изменением.

Код писать постепенно: маленький шаг → diff → подтверждение.

6. Безопасность и отказоустойчивость

Не удалять существующий код без обсуждения.

Не отключать проверки, типизацию и линтеры.

Не менять .env, не генерировать ключи, не пересоздавать Supabase.

7. Коммуникация

Всегда уточнять детали задачи, если есть сомнения.

Писать пошаговое объяснение изменений, если они нетривиальные.
